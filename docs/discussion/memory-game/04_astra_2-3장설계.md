# 04 미지의 세계 — 2·3장 설계 확정 (Astra, 2026-11-15)

**‘미지의 세계’를 3장×10판, 총 30판으로 완성한다. 2장은 짝을 찾으며 엽서를 발견하고, 3장은 발견한 엽서 열 장이 하나의 탐험 지도로 이어진다. 6·8·10쌍의 세 별/두 별 실수 상한은 각각 9/18, 15/28, 23/40회다. 엽서 소장은 기존 완료 기록에서 계산하며 저장 스키마를 변경하지 않는다.**

읽은 자료는 [01 Claude 초안](01_Claude_초안.md), [02 Codex 검토](02_Codex_검토.md), [03 sol 프로토타입 보고](03_sol_프로토타입보고.md), 실제 `src/memory/`의 전체 구현·테스트, 저장·스테이지 선택·앱 연결 코드다. 02·03의 ‘1장까지만’이라는 범위는 이번 사용자의 **30판 완성 지시**로 대체한다. 프로토타입 재승인을 구현의 선행 조건으로 두지 않는다.

이 작업은 설계 문서 작성이다. 다른 저장소 파일은 수정하지 않았으며 앱에 20판을 구현했다는 뜻은 아니다. 아래의 파일별 변경 지시와 검증 항목은 후속 구현자가 수행할 사양이다. 커밋·푸시는 하지 않는다.

## 실제 코드에서 확인한 확장 지점

- [model.ts](../../../src/memory/model.ts)는 12개 `Face`, `MemoryStage`, 순수 reducer, 힌트와 별 계산을 갖고 있다. 성공한 카드는 이동하지 않으며 불일치 중 세 번째 카드 입력도 즉시 받는다. 이 규칙을 유지한다.
- [stages.ts](../../../src/memory/stages.ts)의 1장 10판 ID·크기·그림 세트는 확정 데이터다. 그대로 두고 뒤에 20판을 붙인다. 1장 별 기준도 그대로다.
- [MemoryScreen.tsx](../../../src/memory/MemoryScreen.tsx)에는 ‘짝꿍 보관소’, ‘첫 짝꿍’, `/ 1-10`, ‘첫 짝꿍 10판을 모두 해냈어요!’가 고정돼 있다. 장 정보와 30판 완료 문구로 고쳐야 한다. `allCleared`는 ‘현재 판을 제외한 모든 판이 완료’라는 앱 계약이므로, 1-10·2-10의 장 완료와 3장 전체 완료를 혼동하면 안 된다.
- [MemoryBoard.tsx](../../../src/memory/MemoryBoard.tsx)는 행·열을 이미 데이터로 받는다. 4×5 보드에 새 입력 규칙은 필요 없다. [memory.css](../../../src/memory/memory.css)의 세로로 긴 카드와 큰 여백은 조정한다.
- [storage.ts](../../../src/storage.ts)는 `rail-tiles:progress`, `schemaVersion: 2`, `stars[stageId]`로 완료를 보존한다. 최고 별 병합과 `RT1.` 코드 내보내기가 있으므로 엽서 소장 상태를 중복 저장할 이유가 없다.
- [App.tsx](../../../src/App.tsx)에는 전체 `progress.stars`가 있지만 `GameProps`에는 현재 판의 `bestStars`만 있다. 엽서 목록이 저장소를 따로 읽게 하지 않고, 스테이지 선택 화면에서 앱의 별 기록을 전달한다.

## 장마다 달라지는 재미

### 1장 ‘첫 짝꿍’: 규칙과 기억의 손맛

현재 10판을 유지한다. 짝을 찾으면 그 카드가 그림 면으로 남고 작은 축하가 나온다. 먼저 본 위치를 기억해서 다음 짝을 찾는 보람이 중심이다. 1장에 엽서를 소급해 넣거나, 1장을 다시 깨야 보상을 받게 하지 않는다.

### 2장 ‘그림 너머의 풍경’: 매 판 다른 엽서의 발견

Claude의 **보드 바깥 엽서**를 채택한다. 2-1부터 진행 줄 오른쪽에 작은 풍경을 두고, 짝 하나마다 가림막 한 조각을 걷는다. 2-1은 1장 마지막과 같은 6쌍·기존 그림으로 시작해 새 보상만 먼저 경험한다. 2-2·2-3에서 숲 그림을 두 종류씩 소개하고, 2-4에서 처음 8쌍으로 늘린다.

엽서는 보드 그림의 확대판이나 정답 목록이 아니다. 카드의 짝을 맞추는 활동으로 **처음에는 보이지 않던 장소를 발견한다**는 보상이다. 판마다 풍경 제목과 큰 특징을 다르게 만든다. 단순히 같은 배경의 색만 바꾼 엽서 열 장은 완성 기준을 충족하지 않는다. 2-6에는 6쌍의 짧은 쉬어 가는 판을 둔다.

### 3장 ‘이어지는 세계’: 발견한 장소가 이어지는 탐험

3장도 매 판 엽서를 받지만, 열 장이 정해진 위치에 연결되어 **하나의 세로 탐험 지도**가 된다. 낱장 수집이 지역 전체의 완성으로 바뀐다. 입구 해변 → 등대 → 발사장 → 관측소 → 하늘길 → 항구 → 정원 → 물빛 골짜기 → 별빛 들판 → 도착지 순서다. 새 바다·우주 그림 8종은 처음 네 판에서 두 종류씩 소개하며 이때 보드는 8쌍을 유지한다. 3-5부터 10쌍, 3-7은 8쌍의 정원 휴식이다.

지도의 배치는 위에서 아래로 `1,2 / 4,3 / 5,6 / 8,7 / 9,10`인 두 열 다섯 줄이다. 각 장소를 가로지르는 길의 입구·출구를 이 순서에 맞춰 연결한다. 바깥 테두리, 길과 하늘·지면의 경계가 이어져야 한다. 열 개의 서로 무관한 그림을 격자로 나열하는 것으로 대체하지 않는다. 지도 전체는 엽서 모음에서 보고, 플레이 중에는 **현재 장소 한 칸만** 작게 보여 준다.

3-10 완료 시 마지막 길과 도착 표식이 드러난다. 전체 지도를 아직 다 모으지 않은 코드 복원 상태에서는 ‘이번 장소 발견’을, 열 칸을 모두 소장했을 때만 ‘탐험 지도 완성’을 표시한다. 완성 그림을 보려고 반복해서 세 별을 딸 필요는 없다.

이것은 새 추론 규칙이 아니라 **발견·수집·연결의 재미**다. 핵심 짝 맞추기 규칙은 세 장에서 같다. 이 한계를 숨기면서 ‘3장에는 전혀 다른 퍼즐이 있다’고 설명하지 않는다. 이번 범위에서는 별도의 미니게임보다 안정된 카드 위치와 짧은 판의 리듬을 우선한다.

### 엽서의 정확한 동작

`N = stage.faces.length`, `m = state.matched.length / 2`로 진행을 계산한다. 엽서 컴포넌트는 **엽서 ID와 N·m만** 받는다. `deck`, `seen`, 카드 위치, 마지막 그림 이름, seed를 받지 않는다. 앨범의 지도 컴포넌트는 소장한 엽서 ID 집합만 받는다.

- 6쌍은 **2행×3열**, 8쌍은 **2행×4열**, 10쌍은 **2행×5열**의 가림막을 사용한다. 위 행 왼쪽부터 아래 행 오른쪽 순서로 한 조각씩 제거한다. 보드 격자와 다른 분할이며 특정 카드·짝 종류와 연결하지 않는다.
- 그림의 전체 배경 자산은 고정이다. 첫 발견 전에는 중립적인 종이색과 진행 숫자만 보인다. 카드 실루엣, 카드 좌표, 다음에 찾을 그림, 남은 짝 목록은 넣지 않는다. 동일 stage·m이면 섞인 배치와 성공 순서에 관계없이 **완전히 같은 엽서 상태**여야 한다.
- 짝을 찾은 렌더에서 바로 다음 조각이 보인다. 장식 전환은 최대 180ms의 투명도 변화만 허용하고 입력·완료 기록·다음 버튼을 기다리게 하지 않는다. 카드에서 엽서로 날아가는 효과나 강제 확대 팝업은 없다.
- 불일치·힌트는 엽서를 줄이거나 완성시키지 않는다. 유효 힌트를 사용해도 최종 완료하면 같은 엽서를 받는다. 한 별 완료도 동일하다.
- 완료 시 `m=N`이고 엽서는 즉시 완성된다. 재도전에서는 다시 가린 상태로 시작하지만, 이미 소장한 엽서는 앨범에서 사라지지 않는다. ‘이미 모은 엽서’라는 짧은 표시로 두 상태를 구분한다.
- 판 도중 나가기·새로 섞기는 현재 가림막 진행도만 초기화한다. 부분 엽서는 저장하지 않는다. 재방문 시 새 배치로 시작한다는 기존 안내를 유지한다.
- 장식 SVG와 가림막은 `aria-hidden`, `pointer-events:none`으로 둔다. 기존 `찾은 짝 m / N` 상태 줄에서 진행을 읽는다. 그림 조각마다 별도의 라이브 알림을 중복 재생하지 않는다. reduced-motion에서는 가림막을 즉시 제거한다.

## 별 기준: 큰 판에 기존 공식을 그대로 쓰지 않는다

### 기준 선정과 독립 재실행

02의 실험 결과와 남아 있는 스크립트를 실제로 확인했다. 기준 후보는 02의 시드 `20261115` 결과에서 고르고, **다른 시드 `20261116`으로 각 조건 100,000판을 새로 실행**해 확인했다. 새로운 실행은 N=2·6·8·10 × q=1·0.85·0.65·0.50·0의 20조건, 총 **2,000,000판**이다. N=2는 해석적 검산용이다. 힌트는 사용하지 않았다.

q는 시도 사이에 위치·그림 기억 한 항목을 보존할 확률이다. 매 시도 전에 항목별로 독립적으로 잊고, 기억하는 짝이 있으면 먼저 맞춘다. 없으면 기억하지 못하는 위치를 열고, 상대 위치를 기억하면 선택한다. 모르면 다른 미기억 위치를 연다. 첫 장을 본 뒤의 선택에는 그 공개 정보만 쓴다. 완성한 짝은 선택·기억에서 제거한다. q=0은 이전 시도 정보를 전혀 기억하지 못하는 대조군이다.

q=0.65에서 크기에 따른 세 별 비율의 급락을 줄이고, 두 별 이상은 약 99.8%로 맞춘다. 기존 결과로 후보를 고른 때의 세 별 비율은 81.12/79.83/81.80%였고, 독립 재실행도 80.73/80.01/81.80%로 비슷하다. 완벽 기억은 항상 세 별이며 무기억의 세 별은 큰 판에서 드물다. 상한은 크기별 명시 값으로 두며, 데이터를 맞추기 위한 임의의 다항식을 만들거나 현재 없는 7·9쌍까지 외삽하지 않는다.

**‘모든 아이에게 동일한 체감 난도’가 증명된 것은 아니다.** q=0.50에서는 새 기준이어도 큰 판의 세 별 비율이 낮아진다. 그림 혼동, 위치 혼동, 기억 용량 한계, 피로, 행 순서 탐색은 모델에 없다. q를 연령이나 아이의 능력 점수로 해석하지 않는다. 이 결과가 지지하는 것은 ‘큰 판의 채점 급락을 완화한다’는 판단이다. 보드 크기에 따른 기억 부담 자체를 제거하지는 못한다.

그래서 장 중간에 작은 휴식 판을 두고, 한 별로도 다음 판·엽서를 모두 얻으며, 관찰 시간 옵션과 기존 힌트를 유지한다. 별은 비교 순위나 기억력 검사 점수가 아니다. 실수 상한을 넘었다고 경고음·실패 팝업을 만들지 않는다. 세 별과 두 별 경계, 유효 힌트 시 최대 두 별이라는 안내는 시작부터 공개하고 `starLimits()` 하나를 표시·채점에서 함께 쓴다.

각 조건 100,000판의 비율 표본오차는 95% 기준 최대 약 ±0.31%p다. 반올림된 100.00%는 부분 기억 모델에서 이론적으로 항상 성공한다는 뜻이 아니다. 완벽 기억 모델의 `M ≤ N−1`, N=2 완벽 기억 평균 `2/3`, 무기억 평균 `N(N−1)`을 검산했다. 평균 차이는 표준오차 6배 이내였고, 매 판 `시도=N+M`, 모든 짝 완료, 서로 다른 살아 있는 카드 선택도 검사했다.

```js
// Run: node /tmp/memory04-sim.mjs [trials=100000] [seed=20261116]
// No dependencies. Split board and policy streams; same trial boards across models.
import fs from 'node:fs';
import assert from 'node:assert/strict';
const trials = Number(process.argv[2] ?? 100000);
const BASE = Number(process.argv[3] ?? 20261116);
function rng(seed) {
  let a = seed >>> 0;
  return () => {
    a = (a + 0x6D2B79F5) >>> 0;
    let t = Math.imul(a ^ (a >>> 15), 1 | a);
    t ^= t + Math.imul(t ^ (t >>> 7), 61 | t);
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}
function shuffle(a, rand) {
  for (let i = a.length - 1; i > 0; i--) {
    const j = Math.floor(rand() * (i + 1));
    [a[i], a[j]] = [a[j], a[i]];
  }
  return a;
}
function simulate(board, retention, rand) {
  const remaining = new Set(board.map((_, i) => i));
  const memory = new Map();
  const pick = xs => xs[Math.floor(rand() * xs.length)];
  let misses = 0, attempts = 0, matches = 0;
  while (remaining.size) {
    assert(attempts < 10000, 'nontermination');
    // Between attempts, independently forget each stored position with 1-retention.
    for (const pos of memory.keys()) if (rand() >= retention) memory.delete(pos);
    const byFace = new Map();
    let a, b;
    for (const [pos, face] of memory) {
      if (byFace.has(face)) { a = byFace.get(face); b = pos; break; }
      byFace.set(face, pos);
    }
    if (a === undefined) {
      const unknown = [...remaining].filter(pos => !memory.has(pos));
      assert(unknown.length > 0, 'all known implies a known pair');
      a = pick(unknown);
      // Only revelation reads the hidden board; decision uses memory.
      const face = board[a];
      memory.set(a, face);
      b = [...memory.keys()].find(pos => pos !== a && memory.get(pos) === face);
      if (b === undefined) {
        const choices = [...remaining].filter(pos => pos !== a && !memory.has(pos));
        assert(choices.length > 0, 'an unknown mate must remain');
        b = pick(choices);
      }
    }
    assert(a !== b && remaining.has(a) && remaining.has(b));
    memory.set(a, board[a]); memory.set(b, board[b]);
    attempts++;
    if (board[a] === board[b]) {
      matches++;
      remaining.delete(a); remaining.delete(b);
      memory.delete(a); memory.delete(b);
    } else misses++;
  }
  assert.equal(matches, board.length / 2);
  assert.equal(attempts, matches + misses);
  return misses;
}
const rows = [];
for (const n of [2, 6, 8, 10]) {
  for (const retention of [1, 0.85, 0.65, 0.50, 0]) {
    const boardRand = rng(BASE + n * 1009);
    const policyRand = rng((BASE ^ 0x9e3779b9) + n * 9176 + Math.round(retention * 1000));
    const hist = [];
    let sum = 0, sumSq = 0;
    for (let t = 0; t < trials; t++) {
      const board = shuffle(Array.from({length: 2 * n}, (_, i) => Math.floor(i / 2)), boardRand);
      const m = simulate(board, retention, policyRand);
      hist[m] = (hist[m] ?? 0) + 1;
      sum += m; sumSq += m * m;
    }
    const cdf = cutoff => hist.reduce((s, c, i) => s + (i <= cutoff ? c : 0), 0) / trials;
    const quantile = p => {
      let c = 0;
      for (let m = 0; m < hist.length; m++) { c += hist[m] ?? 0; if (c >= p * trials) return m; }
    };
    const ratings = (three, two) => ({three, two, pct3: 100*cdf(three), pct2: 100*(cdf(two)-cdf(three)), pct1: 100*(1-cdf(two))});
    rows.push({n, retention, trials, mean: sum/trials, meanSE: Math.sqrt((sumSq/trials-(sum/trials)**2)/trials), p50: quantile(.5), p90: quantile(.9), p95: quantile(.95), max: hist.length-1, original: ratings(n,2*n), gentle: ratings(Math.ceil(1.5*n),3*n), adopted: ratings(...({2:[3,6],6:[9,18],8:[15,28],10:[23,40]}[n])), hist: Array.from(hist, x=>x??0)});
  }
}
for (const r of rows.filter(r => r.retention === 1)) assert(r.hist.slice(r.n).every(x => x === 0));
// Analytic sanity checks, not a claim that retention=1 policy is globally optimal.
const two = rows.find(x=>x.n===2 && x.retention===1);
assert(two.hist.slice(2).every(x=>x===0));
assert(Math.abs(two.mean-2/3) < 6*two.meanSE);
for (const row of rows.filter(x=>x.retention===0)) assert(Math.abs(row.mean-row.n*(row.n-1)) < 6*row.meanSE);
fs.writeFileSync(`/tmp/memory04-results-${BASE}.json`, JSON.stringify({baseSeed: BASE, trialsPerCell: trials, model:'independent per-position retention between attempts', rows},null,2)+'\n');
console.log('N q mean p50 p90 p95 max | original 3/2/1% | gentle 3/2/1% | adopted 3/2/1%');
for (const r of rows) console.log(`${r.n} ${r.retention} ${r.mean.toFixed(3)} ${r.p50} ${r.p90} ${r.p95} ${r.max} | ${[r.original.pct3,r.original.pct2,r.original.pct1].map(x=>x.toFixed(2)).join('/')} | ${[r.gentle.pct3,r.gentle.pct2,r.gentle.pct1].map(x=>x.toFixed(2)).join('/')} | ${[r.adopted.pct3,r.adopted.pct2,r.adopted.pct1].map(x=>x.toFixed(2)).join('/')}`);
```

## 엽서 저장과 목록: 별 기록을 단일 원본으로 사용

소장 대상은 **2장 10장 + 3장 10장 = 엽서 20장**이다. 보상 ID는 stage ID 자체를 사용한다. `memory-2-01`에 대응하는 엽서는 영구적으로 같은 엽서다. 1장에는 엽서가 없다.

```ts
// postcardStages는 2·3장의 고정 20개 스테이지만 담는다.
const collected = postcardStages.filter(stage => {
  const rating = stars[stage.id];
  return rating === 1 || rating === 2 || rating === 3;
});
```

새 `postcards` 필드, 새 localStorage 키, 스키마 버전 변경, 별처럼 보이는 가짜 완료 키를 추가하지 않는다. 엽서 완료 기록 때문에 `totalStars`가 올라가면 안 된다. `recordClear(stage.id, rating)` 한 번이 별·해금·엽서 소장을 함께 확정한다. 저장 실패 시 영구 소장이 되지 않는 것은 기존 진행 저장과 동일하며 별도로 성공했다고 꾸미지 않는다.

| 경우 | 확정 동작 |
| --- | --- |
| 기존 1장 10판 완료 저장 | 별·꾸미기·이야기·마지막 판 유지. 2-1이 열리고 엽서는 0/20. 기존 판 재완료 불필요 |
| 2·3장 한 별 또는 힌트 완료 | 해당 엽서를 바로 소장 |
| 같은 판을 더 낮은 별로 재완료 | 최고 별과 소장 유지, 엽서 중복 없음 |
| `RT1.` 내보내기·복원 | 별에서 같은 엽서 목록과 지도 복원. 코드 형식 변경 없음 |
| 다른 탭에서 완료 | 기존 `saveProgress`/`absorbSaved` 별 병합 뒤 앨범도 갱신 |
| 일부 후반 판만 담긴 코드 | 해당 ID의 엽서만 소장. 중간 장소를 자동 발견 처리하지 않음 |
| 현재 없는 stage ID가 별 기록에 있음 | 기존 저장 보존 정책 유지. 현재 엽서 카탈로그 밖의 ID는 소장 개수에 포함하지 않음 |
| 판 도중 이탈 또는 새로고침 | 부분 엽서·카드 상태 미복원. 이미 소장한 완성 엽서는 유지 |

`stories`와 `last.world`의 월드 키는 계속 `memory`다. 게임 이름이 바뀌어도 저장 ID를 `unknown-world` 등으로 바꾸지 않는다. 새 이야기 이름을 보여 주기 위해 기존 `stories`를 지우지 않는다. 사용자가 원하면 ‘이야기 다시 보기’로 새 문구를 본다. 예전 10판 완료자의 `memory:bye` 등 기존 기록도 지우지 않으며, 전체 완료 판정은 현재 30개 ID로 계산한다. 이 기록이 있으면 새 30판 완료 뒤 작별 장면이 자동 재생되지 않을 수 있다. 이 경우에도 완료 결과와 작별 인사 다시 보기 버튼은 제공하며, 재생을 강제하려고 저장 기록을 초기화하지 않는다.

스테이지 선택 화면 헤더 아래에 **‘발견한 엽서 0 / 20’** 펼치기 버튼을 둔다. 모든 엽서 슬롯은 판 순서로 표시한다. 미소장은 중립 종이와 판 번호, 소장은 제목과 풍경을 표시하며 아직 못 깬 판의 정답을 보여 주는 미리보기는 없다. 2장은 개별 엽서 목록, 3장은 연결된 지도다. 소장 그림을 선택하면 큰 그림과 제목을 펼쳐 볼 수 있다. 대화상자나 별도 미니게임은 필요 없다.

앱에서 `progress.stars`를 `MemoryCollection`에 전달하고, 공통 `StageSelect`에는 선택적 `collection?: ReactNode` 표시 자리만 추가한다. 메모리 월드에서만 이 자리를 채운다. 앨범은 저장소를 직접 읽거나 쓰지 않는다. `GameProps` 전체에 메모리 전용 저장 필드를 추가하지 않는다. 플레이 결과 화면은 현재 판의 완성 엽서와 ‘엽서에 담았어요’를 보여 주며, 전체 앨범은 스테이지 목록에서 연다.

## 화면 크기와 그림 식별성

### 4×5는 네 행·다섯 열로 고정

이 문서의 보드 표기는 전부 **행×열**이다. 3장은 4×4→4×5이며 모바일에서 5×4로 자동 전치하지 않는다. 열 수가 바뀌면 위치 기억이 흔들리고 행이 하나 더 길어지기 때문이다. 7쌍·9쌍은 쓰지 않는다. 빈칸을 둔 보드, 한 쌍만 홀로 떨어진 자리, 모바일에서 6·7열을 만드는 직사각형도 이번 범위에는 넣지 않는다.

2·3장 보드의 카드 비율을 **1:1 정사각형**, 보드 안쪽 여백 10px, 간격 8px, 외곽선 1px로 한다. 카드 테두리는 2px, 내부 여백 4px다. 1장에도 6쌍 보드는 같은 밀도 스타일을 적용할 수 있지만 ID·그림·별 기준은 유지한다. 작은 2~4쌍 보드는 기존 비율을 유지한다. 500px 이상에서 보드 최대 폭 440px, 화면 컨테이너 최대 폭 620px는 유지한다.

390px에서는 좌우 화면 여백 18px로 보드 폭이 354px다. 5열 카드 폭은 `(354−22−4×8)/5 = 60px`, 4열은 `(354−22−3×8)/4 = 77px`다. 350px 이하에서는 기존대로 좌우 12px이므로 320px의 5열 카드도 `(296−22−32)/5 = 48.4px`다. `min-height:44px`만으로 폭까지 보장됐다고 판단하지 않고 실제 너비와 높이를 함께 측정한다.

| 화면 폭 | 보드 | 카드 가로×세로 | 앞면 SVG의 CSS 상자 | 보드 높이 |
| ---: | --- | --- | --- | ---: |
| 320px | 4×4 | 62.5×62.5px | 50.5×50.5px | 296px |
| 320px | 4×5 | 48.4×48.4px | 36.4×36.4px | 약 239.6px |
| 390px | 4×4 | 77×77px | 65×65px | 354px |
| 390px | 4×5 | 60×60px | 48×48px | 286px |
| 보드 폭 440px | 4×4 | 98.5×98.5px | 86.5×86.5px | 440px |
| 보드 폭 440px | 4×5 | 약 77.2×77.2px | 약 65.2×65.2px | 약 354.8px |

SVG 상자와 실제 실루엣 크기는 다르다. 기존 viewBox `0 0 64 68`의 비율과 그림 자체의 여백 때문에 실루엣은 표보다 작다. 새 그림은 같은 좌표계에서 큰 실루엣을 사용하고, 가느다란 선·작은 장식·색만으로 구별되게 하지 않는다. 320px의 가장 작은 앞면에서도 알아볼 수 있어야 한다. 성공 체크는 그림 중심을 가리지 않도록 카드 모서리에 두고, 필요하면 5열에서 14px로 줄인다. 체크를 맞추려고 카드 클릭 영역을 줄이지 않는다.

### 세로 공간은 보상을 작게 두어 확보한다

- 맨 위는 뒤로·‘미지의 세계’·소리 버튼, 다음은 장 이름/판 번호와 판 제목이다. 항상 반복되는 ‘같은 그림 두 장…’ 문장은 규칙 영역으로 옮겨 줄 하나를 절약한다.
- 제목 영역 여백은 위 12px/아래 8px, 장 표기는 줄높이 16px, 제목은 26px·줄높이 32px와 위아래 4px 여백을 기준으로 한다. 점수 줄높이 24px, 별 기준은 줄높이 16px·여백 4px 0 10px다.
- 찾은 짝과 엽서는 **높이 64px의 같은 줄**에 둔다. 엽서는 84×56px, 보드와 간격 8px. 최근 찾은 그림을 이 줄에 세 번째로 덧붙이지 않는다. 상세한 풍경 감상은 완료 화면·앨범에서 한다.
- 보드 아래 설명은 최소 높이 24px·줄높이 24px·상하 여백 8px, 도구 버튼은 각각 최소 높이 44px·간격 8px다. 관찰 옵션 위 여백은 4px다. 텍스트가 두 줄이 필요하면 자연스럽게 늘어나며 잘라내지 않는다.
- 가로 스크롤과 보드 내부 스크롤은 만들지 않는다. 짧은 화면·가로 회전·큰 글자에서는 **페이지 세로 스크롤**을 허용한다. 한 화면에 넣으려고 카드를 44px 미만으로 줄이지 않는다.
- 완료 결과는 지금처럼 보드 아래에 즉시 생긴다. 결과 제목에 초점을 옮기고, 화면 밖이면 `scrollIntoView({block:'nearest', behavior:'auto'})` 등으로 결과를 보이게 한다. 다음 버튼은 카드 위에 겹치지 않으며 애니메이션 대기 시간이 없다.

현재 CSS와 위 치수를 조합한 **별도 정적 레이아웃 실험**을 `/tmp/memory04-layout.cjs`에서 Chromium으로 실행했다. 320×568, 390×844, 844×390, 1280×800의 4열·5열 모두 가로 넘침이 없고 표의 카드 치수를 확인했다. 기본 글자 크기의 390×844에서 4×4 보드 하단은 y=617, 도구 버튼 하단은 y=753이었다. 4×5는 각각 y=549·685였다. 320×568의 도구 하단은 각각 y=689·632.6이므로 세로 스크롤이 필요하다.

이 실험은 기존 스타일에 제안 치수를 적용한 가짜 카드·엽서 상자의 측정이며, **미구현 앱 화면이나 새 그림의 식별성 검증을 통과한 것은 아니다.** 결과는 `/tmp/memory04-layout-results.json`에 있다. 실제 구현에서는 긴 힌트 문구, 완료 화면, 글자 200%, safe-area와 실기기 터치까지 확인한다. safe-area 여백을 추가하는 기기에서는 표의 세로 좌표보다 길어질 수 있다.

## 구현 확정 사양

### 범위·이름·데이터

월드 표시 이름은 **미지의 세계**, 월드 ID·theme·emblem 키는 기존 `memory`·`world-memory`·`memory`를 유지한다. 총 30판, 최대 별 90개, 엽서 20장이다. 기존 다른 월드의 해금 조건은 변경하지 않는다. 시간제한, 실패 횟수 제한, 닮은 그림 함정, 콤보 벌점, 중간 셔플, 되돌리기, 일일 퍼즐은 추가하지 않는다.

| 장 | 제목 | start / count | 짝 수 순서 | 보상 |
| ---: | --- | --- | --- | --- |
| 1 | 첫 짝꿍 | 0 / 10 | 2, 2, 3, 3, 3, 4, 4, 4, 6, 6 | 기존 짝 성공 축하 |
| 2 | 그림 너머의 풍경 | 10 / 10 | 6, 6, 6, 8, 8, 6, 8, 8, 8, 8 | 개별 풍경 엽서 10장 |
| 3 | 이어지는 세계 | 20 / 10 | 8, 8, 8, 8, 10, 10, 8, 10, 10, 10 | 연결 지도 엽서 10장 |

`MemoryStage`에 `chapter: 1 | 2 | 3`, `number: 1..10`과 선택적 `postcard` 메타데이터를 추가한다. 엽서 ID는 stage ID이며, 메타데이터에는 풍경 자산 키와 3장 지도 위치를 둔다. 화면 제목을 ID 문자열 파싱이나 `첫 짝꿍` 하드코딩에 의존시키지 않는다. 장 제목은 `MEMORY_CHAPTERS`에서 가져온다. 전체 배열은 장·판 순서로 나열한다.

새 판 ID는 `memory-2-01`~`memory-2-10`, `memory-3-01`~`memory-3-10`이다. 첫 판과 이미 완료한 판은 기존대로 열리고, 다음 판은 직전 판을 **별 하나 이상**으로 완료하면 열린다. 1-10→2-1, 2-10→3-1도 같은 규칙이다. 3-10에는 다음 판 버튼이 없고 목록 버튼을 제공한다. 장 마지막을 기존 스테이지 선택 화면이 ‘보스’로 표시해도 추가 규칙이나 실패 조건은 붙이지 않는다.

### 카드 그림 24종

기존 12종은 그대로 보존한다. 새 12종도 자체 SVG이며 같은 그림 두 복사본의 모양·방향·크기가 완전히 같다. 뒷면은 모든 카드가 같다. 그림 목록의 ID와 앞면·접근성 이름을 같은 정의에서 관리한다.

1장 완료 문구는 ‘첫 짝꿍 10판을 해냈어요!’, 2장 완료는 ‘열 장의 풍경을 발견했어요!’, 30판 전체 완료는 ‘미지의 세계 30판을 모두 해냈어요!’다. 일부 판만 복원한 상태에서는 실제 완료 집합에 맞는 문구를 사용한다. 장 마지막 판이라는 사실만으로 그 장의 모든 엽서를 소장했다고 말하지 않는다. 앱이 현재 장의 나머지 아홉 판 완료 여부를 확인해 기존 `GameProps.clearNote`에 장 완료 문구를 전달하고, 화면은 현재 판 완료 시에만 이를 표시한다. 전체 30판 완료 문구는 `allCleared`로 판단한다. 3장만 전부 완료했으면 장 문구는 ‘탐험 지도 완성!’이다. 이 방식으로 게임 화면에 전체 저장 데이터를 새로 전달하지 않고 부분 복원도 처리한다.

등장 이야기는 ‘미지의 세계에 온 걸 환영해요! / 같은 그림 두 장을 찾아 주세요. / 짝을 찾으며 새로운 풍경을 만나요.’처럼 짧게 쓰고 기존 건너뛰기·재생 기능을 유지한다.

검증은 새 기능의 실제 실패 가능성을 대상으로 한다.

1. **코스·자산:** 3×10판, 고유 ID, 첫 10판 데이터 동일, 모든 판 `rows*cols === 2*faces.length`, 그림 중복 없음, 사용 Face 정확히 24종, 모든 앞면 SVG 존재. 엽서 20개와 지도 10자리의 일대일 대응 확인.
2. **별·기본 입력:** 사용 크기 2·3·4·6·8·10의 경계 직전/정확한 경계/다음 값과 유효 힌트 상한. 8·10쌍에서도 세 번째 빠른 클릭·옛 타이머·재시작·완료 직후 입력이 기존처럼 동작. 900ms 관찰, 120ms 공개, 300ms 성공 축하, 600ms 힌트는 그대로다.
3. **엽서가 답을 누설하지 않음:** 같은 판을 다른 seed와 다른 성공 순서로 m쌍 완료했을 때 엽서 DOM·진행이 동일. 숨은 카드 이름과 좌표·앞면 SVG는 카드 뒷면 DOM에 없음. 앨범·풍경은 미완성 카드 정답을 계산하지 않음.
4. **소장·저장:** 한 별/힌트 완료 즉시 소장, 낮은 재도전·새로 섞기에도 소장 유지, 부분 진행은 소장하지 않음. 기존 저장/RT1 복원/다른 탭 병합 후 같은 목록. 기록 없는 중간 지도 칸은 가림 유지. 다른 월드 별·꾸미기·해금 보존.
5. **장 연결:** 기존 1장 완료 저장으로 2-1 열림, 2-10 한 별로 3-1 열림, 3-10 다음 버튼 없음. 기존 ‘정확히 한 장·10판’ 테스트를 위 30판 표의 구체적 검증으로 교체하며 기존 입력·저장 검사는 유지.
6. **화면:** 실제 앱 320×568·390×844·844×390·1280×800에서 6·8·10쌍, 긴 힌트, 완료 결과, 앨범 검사. 모든 카드 양변 44px 이상, 가로 넘침 없음, 키보드 조작·초점과 큰 글자·reduced-motion 확인. 일반 모션 중 엽서 전환도 입력을 막지 않아야 함. 390px 기본 글자에서는 보드와 힌트/재시작 버튼까지 스크롤 없이 보이도록 검증.
7. **후속 구현 완료 보고:** `npm test`, `npm run build`, `npm run test:browser`, `git diff --check` 결과와 390px의 8·10쌍 플레이/완료/앨범 화면을 남긴다. 현재 문서 작업에서 이 앱 검증들을 수행했다고 보고하지 않는다.

구현자는 위 수치·판별 세트·소장 규칙을 기준으로 30판을 한 번에 완성한다. 새 규칙 승인을 기다리거나 2장 구현만으로 멈추지 않는다. 아이의 실제 반복 의사·그림 식별성은 후속 관찰 대상으로 남기되, 시뮬레이션이 그 관찰을 대신했다고 주장하지 않는다.
