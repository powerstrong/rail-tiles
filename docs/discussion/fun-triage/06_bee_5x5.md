# 06 · 꿀벌의 한붓 꽃길 5×5 재설계

2026-11-15. [03 합의안](03_합의안.md), [04 구현 보고](04_sol_구현보고.md), [05 최종 리뷰](05_astra_최종리뷰.md)를 읽고 “5칸으로 다시” 요청을 적용했다. 작업 트리만 수정했으며 커밋·푸시는 하지 않았다.

## 결과와 난이도 곡선

- 1~20판은 **5열×5행**, 21~30판은 **5열×6행**이다. 가로를 5칸으로 유지해 휴대폰에서 꽃이 작아지는 것을 피했다. 390×844 Chromium 화면에서 마지막 판의 칸은 **63.59×63.59px**였다. 320/390/844px 가로 넘침 검사, 390px 최소 44px 칸 크기 검사, 첫·마지막 판 터치 완주를 통과했다. 벌집 안 잠금 이유 문구도 칸 안에서 줄바꿈하도록 보정했다.
- 첫 3판은 17칸을 사용하는 16수 유도 길이다. 모든 접두 상태에서 다음 전방 이동이 하나이고, 첫 선택 함정과 막다른 상태가 없다. 길의 방향·출발점을 달리해 가로 이동, 꺾기, 가장자리 이동을 익힌다.
- 이후 빈 칸을 줄인다. 4~10판은 빈 칸 6→3개, 11~20판은 2→0개, 21~30판은 더 큰 꽃밭에서 4→1개다. 빈 칸을 배치해 긴 복도만 늘리는 대신 넓은 영역 안에 실제로 틀릴 수 있는 선택을 늘렸다.
- 판마다 저장된 해답을 실제 규칙으로 재생하고 완주를 확인했다. 꿀벌은 모든 유효 칸을 한 번씩 지나므로 모든 완주의 길이는 `유효 칸 수 − 1`로 같다. 따라서 아래 par는 최단 길이이기도 하다.
- 첫 장/둘째 장/셋째 장의 평균 par는 **18.3 / 22.8 / 26.2**, 평균 실제 판단 수는 **3.1 / 7.9 / 10.8**이다. 첫 장 평균에는 입문 3판의 판단 0회가 포함된다. 4판 이후 실제 판단은 3~6 / 7~9 / 10~12회다. 개별 판의 무작위 성공률까지 단조롭게 낮추지는 않았으며, 장 안의 작은 완급은 허용했다.

## 수치의 정의와 선별

**갈림길(실제 판단)**은 저장된 해답의 각 접두 경로에서 합법적인 전방 이동이 둘 이상이고, 그중 완주 가능한 이동과 불가능이 증명된 이동이 모두 있는 지점이다. 정적인 인접 칸 수나 장애물 모서리 수가 아니다. 괄호의 ‘선택’은 둘 이상 합법 이동이 있는 모든 지점으로, 어느 쪽도 풀리는 선택까지 포함한다. 해답 경로에 따라 수가 달라질 수 있으므로 모든 해답에서의 최소 판단 수라고 주장하지 않는다. 후보의 갈림길 판정에 미확인이 있으면 채택하지 않는다.

**무작위 완주율**은 시작부터 그때 합법인 미방문 이웃을 균등하게 하나씩 골라, 완주하거나 더 갈 곳이 없을 때까지 진행한 20,000회 중 완주 비율이다. 벌집 조기 진입은 실제 게임 규칙대로 제외하고, 되짚기·복구·힌트·막힘 경고에 의한 재선택은 하지 않는다. PRNG는 xorshift32, 판별 seed는 `0xbeef0000 + 판 번호`다. 아래는 표본 비율이며 정확한 성공 확률이나 해답 개수는 아니다.

생성 후보는 직사각형 전체를 지나는 경로의 끝을 이웃 칸에 다시 연결하고 일부 경로를 뒤집는 변형을 반복한 뒤 양 끝을 잘라 만든다. 이 방식으로 해답을 가진 빽빽한 후보를 안정적으로 공급한다. 실제 판단 수의 하한/상한을 먼저 검사하고, 4~10판은 최대 `20% / (1 + (번호−4)/2)`, 11~20판은 최대 1.5%, 21~30판은 최대 0.2%인 후보만 남긴다. 채택한 4판 이후 실제 측정 최고값은 각각 7.455%, 1.330%, 0.195%다. 임의로 가도 자주 완주하는 판은 입문 3판으로 제한했다. 해답이 유일해야 한다는 조건은 두지 않았다.

## 판정 성능과 유지한 동작

`src/lab/beeSearch.ts`는 전체 방문 순서 대신 **(현재 칸, 방문 집합 비트마스크)**를 메모한다. 같은 방문 집합과 끝 칸을 가진 경로는 전방 규칙이 같아 같은 증명을 공유한다. 되짚기용 이력은 기존 UI에 그대로 남긴다. 비트마스크와 숫자 키는 6×6의 36칸까지 정확하며, 32비트 비트 연산으로 잘리는 상위 칸도 별도로 검사한다.

각 질의는 연결이 끊긴 남은 영역, 입구와 출구가 부족한 내부 꽃을 먼저 배제한다. 가능 판정에는 실제 후속 완주 경로를 보관하고, 불가능은 구조적 증명 또는 모든 합법 후속 경로의 불가능이 확인된 경우에만 메모한다. 시간·작업량·메모리 상한에 걸린 미확인 상태를 불가능으로 저장하지 않는다. UI 질의는 **6,000개 새 상태 / 8ms**, 판당 메모는 **50,000개**가 상한이다. 시간은 32개 새 상태마다 검사하므로 8ms는 엄밀한 실시간 보장이 아닌 소프트 상한이다. 힌트 Worker도 같은 메모 탐색을 사용하며 자체 작업량 상한 안에서 찾는다.

판 진입 때는 탐색기를 만들고 시작 상태를 질의한다. 큰 전수 그래프·역방향 간선·방문 순서별 상태 배열을 먼저 만들지 않는다. 매 이동은 해당 상태를 메모 조회하거나 제한 탐색한다. 입력의 활성 여부는 판정 결과에 연결하지 않는다. 기존 **가능 / 불가능 증명 / 미확인** 구분, 막힘 즉시 안내, 마지막으로 풀 수 있던 지점 복구, 탭·드래그 되짚기, 한 칸 건너뛰기 거부, 남은 꽃 수와 벌집 잠금 이유가 유지된다. 드래그 이벤트가 합쳐져 중간 상태가 렌더되지 않았어도 복구 이력을 검사하며, 복구 이력 전체가 하나의 6,000상태/8ms 예산을 공유한다.

`npm run lab:bee-audit` 측정: Node v26.13.0 및 headless Chromium 390×844, CDP CPU 4배 감속. 엔진 준비 후 각 판을 빈 메모로 20번 진입했다(환경별 600회). 매번 해답의 모든 접두 상태에서 합법 전방 대안을 질의했다(환경별 19,800회). 진입은 생성자+시작 질의, 이동은 질의 호출만 측정한다. React 렌더·다운로드 시간은 포함하지 않는다.

| 환경 | 진입 최대 | 판별 진입 p95 중 최대 | 이동 질의 최대 | 판별 이동 p95 중 최대 | 미확인(진입 / 이동) |
|---|---:|---:|---:|---:|---:|
| Node | 3.28ms | 3.28ms | 2.78ms | 0.05ms | 0 / 0 |
| Chromium CPU 4배 감속 | 7.40ms | 7.40ms | 3.90ms | 0.10ms | 0 / 0 |

측정 중 한 질의의 새 상태는 최대 **132개**, 판당 메모는 최대 **236개**였다. 실측 원시 값·전체 30판별 분포는 [bee-5x5-audit.json](../../bee-5x5-audit.json)에 있다. 전체 도달 상태 수가 아니라 이 측정 경로의 탐색량이다. 04/05의 ‘꿀벌 전체 7,381개 상태’는 이전 작은 판의 기록이다.

## 남은 문제

1. 실제 초등학생 관찰은 하지 못했다. 낮은 무작위 성공률과 많은 판단 지점은 임의 진행의 쉬움을 배제하는 지표이며, 재미·연령 적합성·재도전 의사를 입증하지 않는다. 특히 첫 3판의 16수 유도 길과 3장의 계획 부담은 아이 관찰로 확인해야 한다.
2. CPU 4배 감속은 실제 저사양 Android/iOS 성능 보장이 아니다. 실기기의 첫 진입, 연속 드래그, 복구 체감을 확인해야 한다. 임의의 모든 잘못된 경로에서 판정이 끝난다고 보장하지 않으며, 상한을 넘는 경우에는 미확인을 유지하고 조작을 허용한다.
3. 무작위 측정은 고정 seed의 표본이며 생성 선별에도 같은 측정을 쓴다. 20,000회 중 3번 같은 작은 성공 횟수는 추정 오차가 크다. 완주율의 소수점 차이를 판 사이 난이도 순위로 해석하지 않는다. 실제 판단 수 역시 제공 해답 경로 기준이다.
